# NIST cryptography in PVS

This workspace contains executable algorithm theories, separate proof developments where needed, saved PVS proofs and tests of generated C. The catalog tracks final FIPS and algorithm-specifying Special Publications as of November 24, 2026. Coverage and assurance are partial. The table gives the scope of each library. NIST publishes algorithm standards and separately validates particular implementations through CAVP. This workspace has no CAVP certificate. [NIST cryptographic standards](https://csrc.nist.gov/projects/cryptographic-standards-and-guidelines) · [CAVP](https://csrc.nist.gov/projects/cryptographic-algorithm-validation-program)

## Catalogue assessment

The source tree contains **186 PVS files in 22 top-level library directories**, excluding backend reproducers. That count includes shared utilities, examples and proof-only theories. Each of the eight algorithm FIPS families in the table has executable source. Coverage varies within publications. SP 800-56B agreement and SP 800-227 composition use the profiles described above. A clause-by-clause mapping from every normative requirement to a PVS declaration is still outstanding.

All fifteen files ending in `_claims.pvs` typechecked in fresh source-only contexts. They contain 48 named lemmas and theorem statements, including authenticated-decryption round trips, signing and verification, conditional KEM agreement and RSA key arithmetic. Further lemmas live with the algorithms. `validation/check_claims.py` typechecks the standalone statements. The AES inverse audit replayed 377 saved declarations across the twenty repository theories enumerated by its runner. General functional correctness proofs for the other libraries remain open. Source quality, lifecycle controls and validation of a deployed module also require evidence outside these theories. The SHA2/SHA3 streaming states, bounded byte arrays, available memory for wide numerals, RSA modulus profile and finite sampling limits determine which inputs each executable entry point accepts.

## Reproduce the checks

Run the commands below from the directory containing this README. They require Python 3, PVS with a built PVS2C runtime, a C compiler with address and undefined-behavior sanitizers, and GMP discoverable by `pkg-config`. The runners select PVS from `--pvs`, then `PVS_BIN`, then `pvs` on `PATH`. If the runtime is installed separately, set `PVS2C_RUNTIME` to its directory containing `include` and `lib`. The scripts build in disposable contexts and preserve the source proof files.

```sh
python3 validation/check.py random ascon sha2 sha3 hmac pbkdf2 ed25519 mlkem
python3 validation/check.py wots slh_verify slh_sign slh_sha2_verify slh_sha2_sign
python3 validation/check.py ec ec-signing rsa rsa-private rsa-kas rsa-keygen
python3 validation/check.py rbg key-generation mldsa kem
python3 validation/check.py --generate-only hash-conditioning mcv bit-derivation
python3 validation/check_claims.py
python3 validation/check_aes.py modes
python3 validation/check_aes.py ccm
python3 validation/check_aes.py gcm_bits
python3 validation/check_aes.py --generate-only fpe
python3 validation/check_assessments.py entropy
python3 validation/check_assessments.py constructions
python3 validation/check_assessments.py sts
```

`validation/check.py` replays local saved declarations and compares generated C results with expected values. The general runner reports operational theories without a saved proof file and checks their generated C. The statistical suites use Boost.Math and a C++17 compiler. The 90B compression statistic also uses libbz2. The assessment runner accepts `CC`, `CXX`, `CPPFLAGS`, `CFLAGS`, `CXXFLAGS` and `LDFLAGS` for toolchains and dependencies outside their default search paths. The 38G wide-numeral theorems are open. The earlier scalar proof scripts are preserved as `.prf.legacy`. Both existing algorithm runners accept `--generate-only` to typecheck, translate, compile and run C independently of proof completion. The [backend reproducer index](reproducers/README.md) describes the observed failure for each case. The AES runner builds the operational dependency chain and runs generated code against vectors. AES inverse proofs also import the NASA PVS Library. Proof-only mathematical theories can use unbounded algebra. Executable inputs use bounded Prelude integer types, byte arrays and length-indexed buffers. The build includes `crypto_prelude/crypto_bits_compat.h` for fixed-width operations for which the tested PVS2C runtime lacks a correct bare C binding.

Type-correctness and termination obligations, the functional lemmas named in each theory, and tests of particular vectors provide different evidence. The present proofs do not establish universal cryptographic security, constant-time execution, secure erasure or entropy quality of an external device.

## Randomness attachments

Load `crypto_prelude/crypto-random-attachments.lisp` before invoking PVS2C on a library that uses the random provider. Link the generated application with two provider functions.

```c
#include <stdint.h>
uint16_t crypto_entropy_lookup(uint64_t stream, uint32_t index);
uint16_t crypto_prng_lookup(uint64_t stream, uint32_t index);
```

Each stream identifies an immutable acquisition. Repeated reads of a given index in that stream must return the same observation, including acquisition failure. Supply fresh stream IDs for independent acquisitions. Values 0 through 255 are octets. The wrappers map larger values to `unavailable`. The provider is responsible for entropy acquisition, approved generator instantiation and source failures. The deterministic providers in `validation/` exist solely to exercise generated C.
