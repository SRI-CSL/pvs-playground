# ML-KEM

The theories implement ML-KEM-512, ML-KEM-768 and ML-KEM-1024. The rank argument is 2, 3 and 4 respectively. The ring, encoding and sampling definitions follow sections 4.2–4.3 and Appendix B. The deterministic key generation, encapsulation and decapsulation entry points implement sections 5–7. The random entry points obtain the 32-byte seeds through the shared PRNG primitive. The caller must supply an approved RBG and a fresh stream for each invocation. [FIPS 203](https://csrc.nist.gov/pubs/fips/203/final)

SampleNTT uses the Appendix B bound of 280 iterations and returns a uniform failure value on exhaustion. Invalid encapsulation keys, incorrect ciphertext lengths and inconsistent decapsulation-key hashes return failure. For a well-sized ciphertext that fails re-encryption, decapsulation returns the implicit rejection secret. The PVS model discards intermediate values on failure. Erasure of released memory and constant-time execution of generated machine code require separate implementation evidence.

The offline fixture contains full public test data for 12 cases. For each parameter set it includes key generation, encapsulation, valid decapsulation and implicit rejection. The full downloaded NIST corpus used for validation contained 240 cases, including key checks. The driver compares complete byte strings. [Key generation corpus](https://github.com/usnistgov/ACVP-Server/tree/master/gen-val/json-files/ML-KEM-keyGen-FIPS203) · [Encapsulation and decapsulation corpus](https://github.com/usnistgov/ACVP-Server/tree/master/gen-val/json-files/ML-KEM-encapDecap-FIPS203)

To exercise additional ACVP vectors, pass both NIST `internalProjection.json` files to `acvp_inputs.py` and feed stdout to `acvp.c` built with the generated C from `mlkem_random.pvs` and the shared PRNG attachments. The SHA-256 checksums of the validated projections were `d7a62a2c3476957f56dd8d24f9004ea6776ccfe995ffe71a65bb9506dc9c7b1b` for key generation and `a556952ce869bb89c3a3196a701dad89647c193a34c86eafb61a9d710d5b810f` for encapsulation and decapsulation.

The typechecked theorem statements in `mlkem_claims` cover generated-key validation, agreement conditioned on correct recovery of the encapsulated message, and the SHAKE256 fallback after failed ciphertext comparison. Their general proofs are open. The conditioning reflects the decapsulation-failure analysis in FIPS 203 section 3.2 and Table 1.
